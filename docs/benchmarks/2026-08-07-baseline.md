# Baseline: giant-PDF generation in Node under t3.small resources

**Date:** 2026-08-07
**Environment:** Docker `node:24-slim`, `--memory=2g --memory-swap=2g --cpus=2` (simulated
t3.small; `local-docker` tag — to be confirmed on a real t3.small). Uncapped curves from an
Apple Silicon Mac (`local` tag). Node v24, qpdf oracle. Raw JSON in `benchmarks/results/`.

**Workload:** canonical "Annual Billing Report" (see `benchmarks/workload/spec.md`) — invoice
ledger with TOC + internal links and per-page `Page X of Y`. Text-only, standard-14 fonts
(no embedding): deliberately the *easiest* case for every contestant.

## Results under the 2 GiB cap

| Runner | mid (~1,144 pages) | full (~11,164 pages) | Failure mode |
| --- | --- | --- | --- |
| pdf-lib 1.17.1 | ok, 476 MB† | **OOM** at 12s | V8 heap exhaustion while materializing the document |
| @react-pdf/renderer 4.5.1 | **OOM** at 10s | **OOM** at 4s | element tree + Yoga layout; 2.86 GB uncapped at mid |
| pdfkit 0.19.1 | ok, 363 MB† | ok, 1,001 MB, 9.7s | survives — see caveats |
| pdfkit shards + pdf-merger-js 5.1.2 | **wrong-output** | **wrong-output**, 683 MB | qpdf passes, but all TOC link destinations are silently dead |

† mid numbers are uncapped local runs; both fit under 2 GiB regardless.

## Interpretation

1. **The memory problem is real and current** (not stale 2019 GitHub-issue lore):
   pdf-lib cannot produce ~11k text-only pages in 2 GiB; react-pdf cannot produce ~1k.
2. **The workaround teams actually use is worse than a crash**: shard-with-pdfkit +
   pdf-merger-js *silently* ships a valid-looking PDF (qpdf --check passes) whose TOC links
   are all dead — pdf-merger-js drops the named-destination tree. Detected mechanically by
   the harness's link-integrity check; this failure is invisible to standard validation.
3. **pdfkit survives, with three asterisks.**
   - The correct output was only possible because the benchmark hand-implements a full
     document pre-pagination pass (`workload/layout.ts`) — every page number and link target
     computed before the first byte is drawn. That module is the authoring pain, and it is
     exactly the two-pass protocol shardpdf's orchestrator productizes.
   - Its RSS still grows linearly (104 MB → 363 MB → 1,001 MB at 72 / 1,144 / 11,164 pages):
     pages stream out, but annotations and the destination name tree accumulate until
     finalize. Extrapolated, pdfkit breaches 2 GiB around ~25k pages of even this workload —
     a shallower slope, not a ceiling.
   - Text-only + standard fonts is its best case; per-page images or embedded fonts steepen
     the slope.
4. **react-pdf also can't express the workload**: no anchor→page API means TOC entries
   cannot show page numbers at all, at any scale.

## What this buys shardpdf

- The soak-test fixture and RSS-capped harness required by the design spec now exist; when
  `crates/core` lands, shardpdf becomes runner #5 against identical workloads and caps.
- Headline comparison for the README, reproducible by anyone:
  `docker run --memory=2g ... --runner all --scale full`.
- The two value claims map one-to-one onto measured failures: bounded memory (vs pdf-lib,
  react-pdf, pdfkit's linear growth) and correct cross-shard references (vs merge's dead
  links, react-pdf's missing TOC numbers).

## Addendum (same day): shardpdf core v0 as runner #5

First vertical slice of `crates/core` (lopdf-based assembler behind napi-rs:
`createAssembly → appendShard → finalize`, with page-tree grafting, inherited-attribute
push-down, and named-destination merging). Same sharded pdfkit rendering as the merge
runner, bound with `@shardpdf/core` instead of pdf-merger-js.

| Runner (local, uncapped, full ~11,164 pages) | Peak RSS | Wall | qpdf | links |
| --- | --- | --- | --- | --- |
| pdfkit shards + pdf-merger-js | 779 MB | 15.0s | pass | **fail — all dead** |
| pdfkit shards + **@shardpdf/core v0** | 754 MB | 18.8s | pass | **pass** |

The cross-shard reference claim is now demonstrated end-to-end.

**Streaming writer (same day, replacing v0's in-memory accumulation):** shard objects now
stream to disk as each shard is parsed; the assembler's working set is one shard plus
byte-offset/page/destination bookkeeping. Isolated bind-only measurement (28 pre-rendered
shards, 11,164 pages, 23.6 MB output, local `/usr/bin/time -l`):

| Bind step only | Peak RSS | Wall | links |
| --- | --- | --- | --- |
| pdf-merger-js | 403 MB (grows with document) | 2.48s | dead |
| **@shardpdf/core (streaming)** | **86 MB (one-shard working set)** | 1.15s | pass |

Whole-runner numbers (683 MB at full) are dominated by the JS side — layout precompute and
pdfkit shard rendering in the same process — which is orchestrator-phase work. Remaining
before the capped Docker matrix includes this runner: Linux prebuilds. The formal soak test
(assert RSS cap over growing document sizes at fixed shard size) lands with the
orchestrator.

## Caveats (kept honest)

- `local-docker` is a resource simulation; EBS/network and CPU steal on a real t3.small are
  not modeled. Confirm headline numbers once on real hardware with `--tag t3.small`.
- Workload is text-only with standard fonts — the *floor* of difficulty. Every failure above
  gets worse with embedded fonts/images; pdfkit's and merge's survivals get weaker.
- pdf-merger-js was tested at v5.1.2; other merge stacks (raw pdf-lib copyPages, qpdf CLI)
  may preserve destinations differently — only the most popular npm path was measured.
